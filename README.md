# Детекция ботов по событиям куки

## Запуск

Python 3.11.0, зависимости в requirements.txt.

```
pip install -r requirements.txt
python train.py
```

`train.py` строит признаки, прогоняет валидацию для всех версий модели и сохраняет submission.csv. Всё вместе идёт около 3 минут. Если валидация не нужна, есть `python train.py --no-cv`, так около минуты.

Основное решение с пояснениями — в `solution.ipynb`: там описание подхода, проверки данных, валидация и сабмит, всё по шагам и с выводами. Ноутбук вызывает функции из двух файлов: признаки в `features.py`, обучение и валидация в `train.py`. `metric.py` взят из архива без изменений.

Папку `data/` из архива нужно положить рядом (в репозиторий я её не добавлял). Сиды везде зафиксированы, я запускал два раза подряд и получил одинаковый сабмит.

Библиотеки: pandas, numpy, scikit-learn, lightgbm. Больше ничего не использовал.

## Что было с данными

Сначала посмотрел на events и нашёл несколько проблем:

1. Примерно 12% событий лежат после window_end_ts. У ботов таких событий 42%, у людей 11%, то есть если их не выкинуть, модель будет учиться на будущем. Оставил только события внутри окна `[window_start_ts, window_end_ts)`.
2. Все captcha_shown оказались после окна, внутри окна капчи нет вообще ни у кого. Так что капча отпала вместе с остальными событиями после окна.
3. 4863 строки — полные дубли. У ботов и у людей их примерно поровну (~3%), так что это похоже на ошибку логирования. Удалил, иначе они портят счётчики и дают интервалы по 0 секунд.
4. Файл не отсортирован по времени, пришлось сортировать внутри каждой куки.
5. platform записан кто как хочет: WEB, Web, web, desktop, iOS, iphone и т.д. Свёл к трём значениям: web, android, ios.
6. Пропуски не заполнял. pointer_x/y бывают только на web, search_query только у выдачи и т.п. LightGBM сам умеет работать с NaN, к тому же сам факт пропуска полезен: например, у ботов на web часто вообще нет координат курсора.

## Признаки

### Поведение внутри окна

Сначала делал только признаки по событиям самой куки.

- Время между событиями. Лучше всего отделяло ботов именно это: у ботов интервалы в основном 3–20 секунд, у людей от 15 секунд до пары минут. Считал квантили интервалов, разброс, долю быстрых и медленных интервалов. Сессии разбивал по паузе больше 30 минут и отдельно брал самую быструю сессию.
- Курсор. У людей x равномерно размазан по всему экрану 0–1920, а у ботов почти всё левее 1300, видимо у headless-браузера маленькое окно. Плюс у ботов часто просто нет курсора. Без этих признаков качество падало с 0.80 до 0.59, так что это самая важная группа из поведенческих.
- Что делает на сайте: доли разных событий, сколько разных объявлений, категорий и городов смотрел, как глубоко листает выдачу (боты уходят на 5–10 страницу и дальше), листает ли подряд 1, 2, 3 по одному запросу.
- Порядок действий: сколько времени проходит после просмотра объявления до следующего действия, как часто подряд идут одинаковые события, как часто меняется город.
- User-Agent. Сырую строку не брал, там 148 вариантов, и модель бы просто их запомнила. Вытащил из неё: headless или нет, curl/python/scrapy, приложение или браузер, версии. Сигнал оказался слабее, чем я ожидал: даже среди кук с HeadlessChrome или curl ботов только 25–50%.
- Возраст куки на момент начала окна.

На этом получилось около 0.80 по метрике. Дальше перебор моделей и гиперпараметров ничего не давал, так что начал разбирать ошибки.

### Какие объявления смотрит кука

Заметил, что боты часто смотрят одни и те же объявления. Примерно 500 объявлений набирают 17% всех просмотров ботов и только 2% просмотров людей. Похоже, сервисы парсят какой-то свой общий список. Проверил, что это не случайность: если посчитать долю ботов по объявлениям за первую неделю, она предсказывает ботов второй недели с ROC-AUC 0.79.

Из этого сделал три группы признаков.

1. Популярность объявлений. Для каждого объявления куки считаю, сколько других кук его смотрели в тот же день или раньше, и делю на число кук за этот период. Метки здесь не используются. Будущие дни не берутся, а все события того же дня уже произошли к концу окна (окна заканчиваются в полночь).
2. Доля ботов по объявлениям (target encoding). Для куки из дня D считаю по объявлениям долю ботов, но только по размеченным кукам из дней раньше D. Для теста получается вся разметка train. Своя метка и метки своего дня в признак не попадают. На валидации это считается заново в каждом фолде только по обучающей части. Пробовал ещё обычный K-fold target encoding, качество такое же, но оставил вариант только по прошлым дням, так честнее.
3. Скор соседей. Сначала обучаю модель на всём вышеперечисленном и получаю скор для всех кук, включая test. Для кук из train скор берётся out-of-fold, чтобы у кук из train в скоре не сидела их собственная метка. Потом для каждой куки считаю средний скор других кук, которые смотрели те же объявления (тоже только до конца её окна), и обучаю вторую модель уже с этим признаком. Идея в том, что в тесте целая неделя без меток, и через соседей туда доходит информация из этих же дней.

### Что не сработало

- Конкретные запросы, категории, города. Доля ботов везде примерно одинаковая.
- Регулярность пауз между сессиями (думал, что боты запускаются по расписанию, но нет).
- Перебирают ли боты item_id подряд. Не перебирают.
- Признаки типа наивного байеса: сумма лог-отношений правдоподобия по каждому событию. По отдельности хорошие, но в модели ничего не добавили, та же информация уже была.
- Другие модели: RandomForest 0.68, ExtraTrees 0.77, HistGradientBoosting 0.79, логрег 0.64. Ансамбли с LightGBM тоже не помогли, поэтому оставил один LightGBM, усреднённый по 5 сидам.
- Гиперпараметры: разница в пределах шума.

## Валидация

Тест идёт по датам сразу после train (train с 6 по 19 апреля, тест с 20 по 26), поэтому валидировал по времени:

- 4 фолда по 2 дня (12–13, 14–15, 16–17, 18–19 апреля), обучение каждый раз на всех днях до фолда;
- отдельно сплит, похожий на тест: учусь на 6–12 апреля, проверяю на 13–19. Так видно, что будет, когда разметка отстаёт на неделю.

Метрику считал функцией из metric.py. Ещё проверил, нет ли сдвига между train и test (adversarial validation): ROC-AUC 0.508, то есть распределения признаков почти одинаковые.

Минус валидации: в одном фолде всего около 70 ботов, поэтому метрика скачет на ±0.03, и мелкие улучшения на ней не видны.

## Результаты

P@R≥0.7:

| | 4 фолда (среднее) | все фолды вместе | сплит 7 дней |
|---|---|---|---|
| baseline из quickstart (RF на n_events и item_nunique) | 0.096 | 0.095 | 0.093 |
| LightGBM, только поведение | 0.799 | 0.767 | 0.755 |
| + популярность и доля ботов по объявлениям | 0.892 | 0.892 | 0.871 |
| + скор соседей (финальная) | 0.902 | 0.895 | 0.883 |

Если просто ставить всем одинаковый скор, метрика равна доле ботов, это примерно 0.08.

У финальной модели по фолдам 0.93 / 0.92 / 0.90 / 0.86, PR-AUC 0.84, ROC-AUC 0.95. На валидации для скорости один сид, в финальной модели пять.

## Ограничения

- На мобильных хуже, чем на web: P@R 0.55 против 0.93. Курсора на телефонах нет, и часть мобильных ботов по событиям выглядит как обычные люди. Думаю, это потому, что разметка сделана по источнику трафика, а не по поведению. С признаками по объявлениям стало лучше, до них было 0.33.
- Около recall 0.7 precision быстро падает: при recall 0.6 она 0.93, при 0.8 уже 0.77. Поэтому на закрытом тесте результат может отличаться от валидации на несколько пунктов.
- Признаки по объявлениям работают, пока боты парсят один и тот же набор. Если он поменяется, они будут хуже до появления новой разметки. С курсором и UA то же самое: если боты начнут лучше имитировать браузер, эти признаки перестанут работать. Модель лучше регулярно переобучать.
